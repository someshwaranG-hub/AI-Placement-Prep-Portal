# Assessment Criteria

## How to Self-Assess Your Solutions

### 1. Correctness (40 points)
- ✓ Does the program produce the expected output?
- ✓ Are all edge cases handled?
- ✓ No runtime errors?
- ✓ Matches sample input/output exactly?

**Scoring:**
- Full marks: All cases pass
- 70%: Most test cases pass
- 40%: Basic cases pass, some edge cases fail
- 0%: Program crashes or no output

---

### 2. Code Quality (30 points)
- ✓ Code is readable and well-organized
- ✓ Variable names are meaningful
- ✓ Functions are properly structured
- ✓ Follows language conventions
- ✓ Proper indentation and formatting
- ✓ Comments where necessary

**Scoring:**
- 30/30: Excellent code quality
- 25/30: Good, minor style issues
- 18/30: Acceptable, some readability issues
- 12/30: Poor structure, hard to follow
- 0/30: Unreadable code

---

### 3. Efficiency (20 points)
- ✓ Time Complexity: Is it optimal or acceptable?
- ✓ Space Complexity: Not using unnecessary extra space?
- ✓ Algorithm efficiency: Is it the intended approach?

**Scoring:**
- 20/20: Optimal solution
- 16/20: Good efficiency, minor improvements possible
- 12/20: Acceptable for beginner level
- 8/20: Works but inefficient
- 0/20: Very poor efficiency (timeouts)

---

### 4. Best Practices (10 points)
- ✓ Error handling present?
- ✓ Input validation?
- ✓ Following SOLID principles?
- ✓ No code duplication?
- ✓ Resource management (closing files, etc.)?

**Scoring:**
- 10/10: Excellent practices
- 8/10: Good practices, minor gaps
- 5/10: Acceptable practices
- 0/10: No consideration for best practices

---

## Self-Assessment Checklist

For each problem, ask yourself:

### Before Running Code
- [ ] Do I understand what the problem is asking?
- [ ] Have I thought about the approach/algorithm?
- [ ] Have I considered edge cases?
- [ ] Have I written pseudocode?

### After Writing Code
- [ ] Does the code compile without errors?
- [ ] Did I test with provided examples?
- [ ] Did I test edge cases?
- [ ] Is my code readable?
- [ ] Are variable names clear?

### Before Submitting
- [ ] Time Complexity: Is it acceptable?
- [ ] Space Complexity: Am I using extra space efficiently?
- [ ] Code Quality: Would I be proud to show this in an interview?
- [ ] Comments: Is my code self-explanatory?

---

## Progress Evaluation

### Weekly Self-Review
1. How many problems did I complete?
2. How many did I solve without looking at solutions?
3. What topics were challenging?
4. What did I learn?
5. What do I need to practice more?

### Monthly Goals
- **Month 1:** Complete all Beginner problems (12-15 problems/language)
- **Month 2:** Complete all Intermediate problems (8-10 problems/language)
- **Month 3:** Complete all Advanced problems (8-12 problems/language)

### Self-Rating Scale

After completing a problem, rate yourself:

**5 Stars** ⭐⭐⭐⭐⭐
- Solved independently
- Optimal solution
- Clean code
- Good explanation

**4 Stars** ⭐⭐⭐⭐
- Solved with minimal hints
- Good solution
- Acceptable code quality

**3 Stars** ⭐⭐⭐
- Needed some help
- Solution works but not optimal
- Code needs improvement

**2 Stars** ⭐⭐
- Needed significant help
- Solution barely works
- Poor code quality

**1 Star** ⭐
- Couldn't solve without looking at solution
- Needs complete rework

---

## Moving to Next Level

You're ready to move to the next level when:

1. ✓ 80%+ problems solved independently
2. ✓ Average rating ≥ 3.5 stars
3. ✓ Consistent code quality
4. ✓ Able to optimize solutions
5. ✓ Can explain solutions clearly

---

## Interview Readiness Assessment

### Before Interviews, Ensure:
- [ ] Can solve 90%+ of problems in your current level
- [ ] Can code without external resources
- [ ] Can explain time/space complexity
- [ ] Code is clean and interview-ready
- [ ] Can handle follow-up questions
- [ ] Know multiple approaches for common problems
